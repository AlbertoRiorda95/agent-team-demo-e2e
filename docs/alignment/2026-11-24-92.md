## What changed
store now applies its own config (`docs/design/persistence.md`, task row 3):
it answers `config.store.set` on `config.store.applied`, keeps the config in
force in a local file at `STORE_CONFIG_PATH`, and opens the sealed DB
credentials with `STORE_CONFIG_KEY`.

## What the others relied on (before → after)
- Environment (deployment interface): `DATABASE_*`, `NATS_URL` → also
  `STORE_CONFIG_PATH` (optional, default `/var/lib/store/config.json`; the
  folder must be writable by uid 10001) and `STORE_CONFIG_KEY` (base64 of 32
  bytes, `openssl rand -base64 32`). Without the key store still runs but is
  `degraded` (`STORE_CONFIG_KEY missing or invalid`) and refuses sets with
  credentials (`no config key`). In today's compose (`read_only: true`, no
  volume, no key) store is `degraded` and every set that changes something
  answers ok = false `cannot save the local config file: ...`. Trajectories
  are still stored. Persistence row 4 (devops) fixes both.
- NATS: nothing on `config.store.*` → store subscribes to `config.store.set`
  (core, new messages only) and publishes a `ConfigApplied` (payload `store`,
  `db_credentials_sealed` always empty) on `config.store.applied` at start-up
  and for every set. The `CONFIG` stream keeps the latest, so the viewer (M3)
  can read the prefix in force from it.
- `status.store`: `config_version` 0 → the version in force; two new
  `detail` reasons: `STORE_CONFIG_KEY missing or invalid`, `local config file
  invalid`.
- Data model: a set with a new prefix creates `<prefix>launches`,
  `<prefix>trajectory_samples` and `<prefix>flyway_schema_history` next to the
  old tables (kept as they are). This is the V2 schema from #91, not a new
  migration.
