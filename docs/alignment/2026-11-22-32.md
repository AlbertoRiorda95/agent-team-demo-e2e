## What changed
The NATS contract `trajectory.v1` exists (`proto/trajectory/v1/`), with its
subjects, encoding and `Nats-Msg-Id` rule in `proto/README.md`, and the four
JetStream streams as JSON in `proto/nats/streams/`.
`@albertoriorda95/trajectory-proto` is 0.1.0 and exports the types and the
subject constants. Additions only; `demo.v1.Ping` is only deprecated.

## What the others relied on (before → after)
- Stream provisioning (devops, contracts row 2): nothing →
  `proto/nats/streams/{LAUNCHES,TRAJECTORIES,ERRORS,CONFIG}.json`, each a
  JetStream stream config that `nats stream add --config <file>` accepts.
  Checked against `nats:2-alpine` with `natsio/nats-box`: the loop
  `for f in /streams/*.json; do nats stream add --config "$f"; done` creates
  the four streams with the settings of the table in `proto/README.md`.
  `nats-init` mounts or copies `proto/nats/streams/` and runs that loop; to be
  re-runnable it can skip a stream that `nats stream info <NAME>` already finds.
- NATS server: the largest `TrajectoryComputed` (100000 samples) is about
  7 MB as binary (test in `libs/trajectory-proto`), so NATS needs
  `max_payload` 8 MB (8388608), as the spec says; the default 1 MB rejects it.
- Library consumers (web servers, backend): `@albertoriorda95/trajectory-proto`
  0.1.0 in the workspace; the user pushes the tag `v0.1.0` after the merge to
  publish it (agents never tag). Its tests now run with Vitest (`vitest`
  5.1.1, already in the lockfile).
