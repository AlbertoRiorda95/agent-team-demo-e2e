## What changed
The design of kubernetes-deployment (M6) changes what the control-web
frontend, the propagator, store and ros2-publisher services, and the
deployment must provide. The DB write credentials of store come only from a
Kubernetes Secret, so the control page field for them is disabled with a note;
Start restores a baseline replica count instead of 1; three services get an
HTTP health listener.

## What the others relied on (before → after)
- control-web UI (M4): the store Config form accepted DB write credentials
  (write-only) → in Kubernetes the field is disabled and shows "Managed by a
  Kubernetes Secret. To change them, update the Secret and restart store.";
  the other store settings stay editable. The M4 control-panel spec must
  handle the disabled field.
- control-web server API (M4): `GET /api/config/store` had no flag → it also
  returns `credentials_managed` (boolean, additive, from
  `CREDENTIALS_MANAGED`).
- control-web server (M4): Start scaled a deployment to 1 (`project.md` flow
  7) → Start scales to the annotation `trajectory/baseline-replicas` (2 for
  api, viz-web, propagator and store; 1 for the others); Stop still scales
  to 0.
- store (M2): applied any `config.store.set`, credentials included → with
  `CREDENTIALS_MANAGED=true` it refuses a message with a credentials payload
  (`config.store.applied` with `ok=false`, "DB credentials are managed by a
  Kubernetes Secret") and reads its credentials from the environment.
- propagator, store, ros2-publisher: no HTTP health endpoint (foundations) →
  `GET /healthz` on the new environment variable `HEALTH_PORT` (default
  8081), 200 ok or 503 degraded; they also read the latest config message at
  start-up.
- Environment: new `HEALTH_PORT` and `CREDENTIALS_MANAGED` in `.env.example`.
