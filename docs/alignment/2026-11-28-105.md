## What changed
store migration V3 (`V3__trajectory_reader_role.sql`, viewer.md task row 1)
creates the NOLOGIN role `trajectory_reader` if it does not exist and grants it
`SELECT` on `<prefix>launches` and `<prefix>trajectory_samples`, for every
prefix that migrates (each prefix runs its own V3).

## What the others relied on (before → after)
- Data model: no read-only role → the cluster-wide role `trajectory_reader`
  (NOLOGIN, SELECT only on both tables of every migrated prefix; no INSERT,
  UPDATE, DELETE, TRUNCATE). No table changes.
- Deployment interface: on the first V3 run the migrating user
  (`DATABASE_USER` of store) needs `CREATEROLE`, or the role must already
  exist. Today's compose uses `POSTGRES_USER` (superuser of the image): fine.
  A dedicated non-superuser store user (M6) needs `CREATEROLE`, or a
  `CREATE ROLE trajectory_reader NOLOGIN` before store starts.
- The login user `viz_web` is not created by store: `GRANT trajectory_reader
  TO viz_web` is up to the compose `db-init` (viewer.md row 4). Since the
  `db-init` may run before store has migrated, it should also create the role
  if it is missing (same statement as V3), so the `GRANT` never fails.
