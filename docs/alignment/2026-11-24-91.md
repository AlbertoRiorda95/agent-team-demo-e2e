## What changed
store now consumes `trajectories.computed` and writes the trajectories to
PostgreSQL (`docs/design/persistence.md`, task row 2): Flyway
`V2__launches_and_samples.sql` creates `<prefix>launches` and
`<prefix>trajectory_samples` (prefix empty for now), it answers on
`trajectories.stored` and `pipeline.errors`, and sends the `status.store`
heartbeat every 5 s.

## What the others relied on (before → after)
- Data model (read only by the viz-web server history, viewer M3): no tables →
  `launches` and `trajectory_samples` exactly as the spec's Data and API
  tables, `status` always `stored` in M2; constraint and index names carry the
  prefix (`launches_pkey`, `launches_received_at_idx`,
  `trajectory_samples_launch_id_fkey`...). One Flyway history per prefix:
  `<prefix>flyway_schema_history` (the default prefix keeps
  `flyway_schema_history`, so the V1 baseline database upgrades in place).
- NATS: `trajectories.stored` (`TrajectoryStored`, `Nats-Msg-Id` = launch_id),
  `pipeline.errors` (service `store`, subject `trajectories.computed`) and
  `status.store` (`ServiceStatus`, `detail` = `database unavailable`, `not
  connected to NATS`, `consumer not ready`, joined by "; ") are now published.
  The durable consumer `store` on `TRAJECTORIES` is created by store itself
  (explicit ack, ack wait 60 s, no max deliver); store retries with backoff until
  the stream exists (nats-init creates it, as today).
- Deployment: unchanged. No new port or variable; the image builds from
  `src/main` as before (the generated Java code is committed in
  `src/main/generated/`, checked by `docker build` and `docker run`).
- `ServiceStatus.config_version` is 0 until the store config (task 3, #92).
