## What changed
Every service has a `services/<name>/Dockerfile` and runs in `compose.yml`
(`docker compose up --build`). `services/viz-web/server` is now an npm
workspace. Two host-port variables are new in `.env.example`.

## What the others relied on (before → after)
- Image build interface: nothing → every Dockerfile is built with the
  **repository root** as its context (`docker build -f
  services/<name>/Dockerfile .`, `ci/build-images.sh`), and copies only what
  its `services/<name>/Dockerfile.dockerignore` allows. A service that needs
  new files in its image (for example `gen/` from `npx buf generate` in M1)
  asks devops to add them to its Dockerfile and its ignore file.
- Root `package.json` workspaces: `services/viz-web/server` was not one →
  it is now one (the follow-up proposed in `2026-11-20-8.md`). `npm ci`
  installs it, root `npm test` and `npm run typecheck` run its scripts, the
  lockfile records its `fastify`.
- `.env.example`: new `VIZ_WEB_SERVER_PORT=3001` (the variable the viz-web
  server already reads; compose publishes the container's 3001 on it) and
  new `CONTROL_WEB_SERVER_PORT=3002` (host port compose publishes the
  control-web server's container port 5174 on). Container ports and in-image
  variables (`API_HOST=0.0.0.0`, `VIZ_WEB_SERVER_HOST=0.0.0.0`, the ports)
  follow what each service already reads; no service code changed.
- Healthchecks: api, viz-web and control-web use `GET /healthz` (200 healthy,
  anything else unhealthy). propagator, store and ros2-publisher have no
  probe, so their Docker healthcheck is **process liveness only** (`kill -0
  1`): this is the "process-liveness healthcheck" option of
  `2026-11-22-5.md` and `2026-11-22-7.md`, the one that needs no code. If
  designer chooses a probe (HTTP or a health file), backend adds it and
  devops switches the healthcheck.
- Runtime users: api, propagator, ros2-publisher, store run as uid 10001;
  viz-web and control-web as the Node image's `node` (uid 1000). All
  containers run with a read-only root filesystem in compose; only `/tmp` is
  writable (tmpfs) where a service needs it (api, store: JVM, ros2-publisher:
  `ROS_HOME=/tmp/ros`). A service that starts writing elsewhere fails.

## Found while doing this (for the owners)
- Selecting viz-web by folder: `-w services/viz-web` now also selects the
  nested `services/viz-web/server` workspace. Scripts the server lacks fail
  (`Missing script: "build"`): this broke the `ui` job, fixed by selecting the
  apps by package name in `playwright.config.ts`
  (`-w @agent-team-demo-e2e/viz-web`). The commands in `AGENTS.md`
  (`npm run dev -w services/viz-web`, `npm test -w services/viz-web`) hit the
  same thing: `dev` fails, `test` also runs the server's tests. Use the
  package name, or give the server those scripts (backend, `AGENTS.md`: lead).
- control-web: the server reads `CONTROL_WEB_PORT` (default 5174), the same
  variable and port as the Vite dev server of the UI (`.env.example`,
  `npm run dev -w services/control-web`). On the host both cannot run at once.
  In compose this is avoided (host port 3002), but a separate variable for the
  server (as viz-web has with `VIZ_WEB_SERVER_PORT`) would be clearer:
  backend's code, frontend's dev script.
- viz-web and control-web images run the server only. Neither server serves
  the built UI bundle yet, so the UI is not in the images: when the servers
  serve `dist/`, devops adds the `vite build` stage.
